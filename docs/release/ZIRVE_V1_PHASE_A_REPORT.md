## Подтверждённые проблемы и исправления

Историческая причина `fetch error` остаётся неизвестной. В коде были подтверждены два последовательных ожидания staging DELETE, отсутствие явных сетевых deadlines, смешение ошибок, небезопасное удаление оригиналов при неизвестном результате SQL COMMIT и отсутствие устойчивого replay создания. Эти дефекты исправлены; Sharp не объявляется причиной исторического сбоя.

- Успешный save больше не ждёт staging DELETE. Удаление файлов, исключённых из бюллетеня, также передано существующему orphan sweep.
- Оригиналы получают новые серверные immutable keys. Подписанный PUT разрешён только для staging, поэтому его повторное использование не перезаписывает опубликованный оригинал.
- При неизвестном SQL/HTTP ACK сначала проверяется сохранённое состояние. Оригиналы после потенциального COMMIT не удаляются. Если recovery-соединение также недоступно, возвращается безопасная ошибка неизвестного результата, допускающая повтор с прежним ключом.
- S3 SDK: connect 3 с, socket 5 с, request 15 с, максимум две попытки; общий operation signal ограничивает совокупное ожидание. PUT/GET — 15 с, DELETE — 2 с, LIST — 30 с. Потоки ограничены общим временем, idle timeout и точным количеством bytes; таймер остаётся активным после получения headers.
- Финализация одного фото имеет бюджет 45 с; SQL использует statement timeout 5 с и lock timeout 1,5 с. Все серверные действия ожидаются в HTTP-запросе. Новых фоновых Promise после ответа нет.
- Разделены validation, storage, timeout, cancellation, занятый обработчик, processor, conflict и unknown. На клиенте отдельно различаются транспорт и Storage PUT. Необработанные provider/framework exceptions не выводятся пользователю.
- Логи содержат request ID, стадию, длительность, код и размер; содержимое документа, имена, storage keys, signed URLs и секреты в новую диагностику не включены.

## Оригиналы и Sharp

Сохранены лимиты 10 фото по 10 MiB, проверка MIME/signature, полного декодирования, размеров, количества пикселей/каналов и запрет анимации. Сохраняются исходные bytes и SHA-256 оригинала. WebP для JPG/PNG — оптимизация: ошибка кодирования или PUT производной копии допускает сохранение проверенного оригинала.

Sharp остаётся существующей локальной Node.js-библиотекой: не добавлены subprocess, сервис или зависимость. Ограничены одновременно работающие обработчики приложения (2), потоки libvips (1), cache и native decode/encode timeout (5 с). Есть signal checkpoints до публикации. Ограничение: ожидание native очереди/libuv и некоторые native операции нельзя принудительно прервать JavaScript AbortSignal; это не hard-kill гарантия процесса.

## Additive schema и реально применённая миграция

На **основной настроенной БД разработки**, в рамках расширенного разрешения пользователя, применена только [0029_document_image_reliability_expand.sql](../../drizzle/0029_document_image_reliability_expand.sql).

Созданы три таблицы: `document_creations` (durable receipt), `document_image_uploads` (slots/leases/generations), `image_upload_objects` (защита кандидатов от cleanup). Добавлены уникальные ограничения, FK/check constraints, индексы срока хранения и uploader. RLS включён, права PUBLIC и существующих anon/authenticated отозваны. Существующие таблицы/данные не переписывались.

Перед применением проверены текущая схема, hash предшествующей `0028`, последний Drizzle journal и отсутствие конфликтующих таблиц; миграция и запись journal выполнены одной транзакцией с advisory lock и SQL timeouts. После применения проверены три таблицы с RLS, 15 constraints и **полная схема приложения: 0 расхождений**. Одна синтетическая object-запись подтвердила доступ к одной схеме из migration/runtime подключений и удалена. Существующие документы, вложения, пользователи и S3-объекты не изменены. [Машинный результат](ZIRVE_V1_DB_CHECKS.json).

## Cleanup и гонки

Существующий cron сохранён. Перед DELETE повторно проверяются ссылки обеих attachment-таблиц, включая WebP, активная session/lease и protection window. Cleanup берёт object lock и переводит объект в `deleting`; finalize берёт тот же lock и не публикует такой объект. Сетевой DELETE выполняется после короткой транзакции. Удаление документа, отмена и новая generation блокируют старую финализацию. Объекты после неизвестного COMMIT остаются для reference-aware sweep.

Адресные проверки: `operations.test.ts`, `s3.test.ts`, существующие image-upload/Sharp/orphan tests, `attachments.test.ts`, `image-lifecycle.integration.test.ts`. TypeScript, ESLint и production build проверены также для общего результата A–D; точные итоговые числа — в [общем отчёте](ZIRVE_V1_RELIABILITY_UX_GALLERY_REPORT.md).
