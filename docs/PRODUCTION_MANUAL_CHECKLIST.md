3. **Подтвердите production SHA.** GitHub main должен включать merge PR #1 и необходимые docs followups. Откройте production deployment → Source/Commit и сравните полный SHA с `git ls-remote origin refs/heads/main` на момент принятия релиза. Проверьте, что production domain назначен именно этому deployment. Результат Git push, login200 и signed Inngest GET сами по себе SHA не доказывают. При наличии штатного metadata проверьте `VERCEL_GIT_COMMIT_SHA`/`VERCEL_ENV`, не создавая публичный debug endpoint.

4. **Deployments → production deployment.** Требуются READY/success, правильный source и production domain. Просмотрите Build Logs; артефакт должен использовать Node 22, streaming analytics function с maxDuration 120s и Inngest function с 300s (`vite.config.ts`). Проверьте фактические region и доступные hosting limits. Старый main `a45706e…` имел blocked deployment; это historical evidence, а не статус нового merge.

5. **Deployment → Logs / project Logs (Function Logs).** Отфильтруйте нужный deployment и время запроса, `/api/analytics/search` и `/api/inngest`. Сохраните доступные безопасные поля и correlation ID. В коде `console.error` редактирует строки/объекты и сообщения ошибок; некоторые provider детали в logs могут отсутствовать. Если метаданных недостаточно, фиксируйте этот пробел явно и используйте Google/Inngest console; не включайте raw error/prompt logging.

6. **Безопасно воспроизведите известный Gemini failure.** Используйте отдельного пользователя с clearance **open** (также для admin: повышенный clearance консервативно запрещает внешнюю обработку query). Создайте только новый synthetic open документ с уникальным маркером, например `RC-<UTC>-<random>`, и текстом: «Bu, uydurma açıq sınaq qeydidir. 21 oktyabr 2026 tarixində sınaq sayı 42 olub.» Дождитесь настоящего cloud indexing `ready`. В Analitika включите режим ответа и спросите по уникальному маркеру дату и число. В Network сохраните только типы SSE событий, HTTP status, `x-analytics-request-id`, время, duration и безопасный текст ошибки. Последний actual preview результат: **`sources → error`, validated `final` отсутствует** ([PREVIEW_SMOKE.json](release/PREVIEW_SMOKE.json)). Новый успех должен быть зафиксирован отдельно; sources-only final генерацией не является. Не используйте закрытый corpus для диагностики провайдера.

7. **Диагностируйте без секретов.** Запишите доступные deployment SHA/ID/region, request ID, stage (retrieval/generation/validation), configured и фактически завершившую model, provider HTTP status, timeout/abort, quotaKey/limitKind, Retry-After, номер validation attempt и counts ошибок citations. В Google console проверьте quota/billing/API availability нужного project. Если поле недоступно, отметьте NOT VERIFIED; причиной нельзя автоматически считать неверную модель, quota или env. Не сохраняйте API keys, DB URLs, Cookie/Authorization, signing keys, signed/bypass URL query, prompts, full sources или raw provider errors. Локальные primary/light200 и три generation PASS не закрывают actual preview failure.

8. **Подтвердите ответ и citations.** Для того же open fixture должны появиться валидный SSE `final`, правильные 42/дата, citations `[n]`, переход к правильному parent UUID/фрагменту и доступное изображение. History должна содержать terminal `done` и фактическую завершившую model (в том числе light при quota fallback). Отдельно проверьте no-answer на отсутствующий факт, cancel и error/deadline без ложного финального ответа. Structural/excerpt/numeric checks не являются semantic entailment; вручную сопоставьте claims с source. Повторите на фактическом production deployment, не только preview.

9. **Inngest → app `analitika`, нужный production environment.** Sync URL должен указывать на текущий production `/api/inngest`; sync только подписанный, unsigned GET/POST не должны становиться unauthenticated endpoint. Подтвердите ровно шесть функций (UI может показывать prefix `analitika-`):

   | `process-document`               | `document/indexing.requested` |

   | `requeue-stale-document-indexes` | `*/15 * * * *`                |
   | `cleanup-orphaned-uploads`       | `0 2 * * *`                   |

   Последнее наблюдение production — восемь старых функций, без document recovery. `run-osint`, `close-stale-osint-runs`, `retry-osint-summary` должны отсутствовать в актуальном наборе и не запускаться. Их pause HTTP200 ранее подтверждён лишь acknowledgement, не state readback. Не resync старый deployment. Signed GET с шестью функциями ещё не доказывает cloud registration или выполнение.

10. **Events / Runs → настоящий lifecycle.** Создайте новый open document и brief через production UI. Зафиксируйте точные source/event/run IDs; cloud events должны доставиться, jobs завершиться, записи перейти queued → processing → ready, chunks/embeddings появиться без duplicate ordinals. Не вызывайте local worker вручную для этой проверки. На отдельных exact fixtures проверьте duplicate/retry, queue failure/lost event и recovery после настоящего worker/process restart. Код использует document stale threshold 6min, brief 15min, failed wait 30min, максимум пять recovery attempts; scheduler раз в 15min не обещает мгновенный retry. Старые committed chunks должны сохраняться при ошибке, stale lease не должен финализировать новую версию, edited brief не должен выдавать старый текст. Не запускайте global recovery/reindex и не прерывайте пользовательские jobs ради теста. Удалите только собственные fixture records/history/objects по точным IDs; corpus compare должен сохранить 13 documents / 10 briefs / 107 chunks, если владелец за это время не добавлял реальные данные.

11. **Auth, clearance и private storage на production.** Проверьте login/logout/expiry/deactivated session, Secure+HttpOnly+SameSite=Lax cookie и admin settings. Пользователь open, включая owner/admin, не должен читать, менять, удалять или retry чужой по clearance secret document по прямому UUID/API, attachment или history. Xülasələr catalogue — lexical AND PostgreSQL: AZ case/NFC/i/ı/ə, слова в title/body, date/month, pagination и empty-state; LLM/vector/rerank здесь не вызываются. Загрузите synthetic JPG/PNG/WebP ≤10MiB: authenticated GET работает, unsigned/public access запрещён, неправильные MIME/size/signature отвергаются, повторный staging PUT/discard не меняет committed image. Bucket остаётся private; bucket-level MIME/size limits ранее unset, server validation/signature обязательны. Retired `/osint` и `/sorgu` дают404 после auth. Удаляйте только созданные тестом объекты.

12. **Подтвердите rollback.** В Deployments найдите доступный previous READY deployment с полным SHA и рабочим rollback/promote механизмом; проверьте совместимость с текущей DB и согласованность Inngest sync. Historical candidate: commit `a2af6269d81e57e839ecc226e7e1a8ae0014f10f`, deployment `2VnHomtKSpAHZ3BcLR373qUBiDp2` — **не подтверждённый рабочий rollback target**. Не выбирайте старый runtime вслепую: он может вернуть retired функции или прежние defects. Запишите кто и как выполнит rollback при критическом smoke failure. Не делайте schema downgrade/reset; applied SQL и corpus сохраняются. DB backup/PITR/restore readiness отдельно подтвердите в Supabase без restore поверх текущего corpus.

13. **Production GO только после evidence.** Требуются current production SHA/READY/env, успешная actual Gemini generation с citations и no-answer, шесть актуальных cloud jobs и реальные document/brief/recovery runs, production auth/clearance/private storage smoke, fixture cleanup/DB integrity и рабочий rollback. Critical FAIL/NOT VERIFIED не должно оставаться. Пока preview generation cause, production revision/env, cloud registration/delivery/restart или rollback не подтверждены, итог остаётся **PRODUCTION VERIFIED: NO / NO-GO**, даже если CODE READY и GitHub main обновлён.
